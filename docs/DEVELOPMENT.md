# HaulBoard Development

## Working on the page

`index.html` is the whole product: one self-contained HTML file with inline CSS and JS. There is no build step, no framework, and no dependency to install — edit the file, open it in a browser, and what you see is exactly what ships.

House style ("Market Ledger"):

- Colors: deep green `#14532d` / green `#166534`, warm cream `#f6f3ec`, marigold `#d97706`
- Headings in Georgia serif; body in the system sans stack
- Mobile-first, single column under 760px, app-style views with a tab bar (fixed bottom bar on mobile, top pill bar at 761px+), 44px+ tap targets
- No external fonts, scripts, images, or trackers — ever. New assets must live in this repo and be referenced relatively

The PWA files are deliberately tiny and boring:

- `manifest.webmanifest` — name, short name, colors, `display: standalone`, icon entries
- `icon.svg` — the app icon (also used as the Apple touch icon)
- `sw.js` — network-first for navigations (fresh board wins), cache-first for the icon/manifest, cache name versioned (`haulboard-v<major>`); bump the version when the shell changes so phones drop the old cache
- `.nojekyll` — empty file; without it GitHub Pages runs Jekyll over the repo for no benefit

## Validation checklist (before every push)

1. HTML parses with no unclosed tags; doctype first, `</html>` last
2. Hash-router compatibility (replaces the old section-id rule): every legacy hash (`#top-picks`, `#al-aqsa`, `#wfw`, `#more-stores`, `#big-retailers`, `#watchlist`, `#price-compare`, `#coupons`, `#free-food`, `#my-list`), the `#compare` and `#stores` aliases, and all 15 store slugs route to the right view or store detail per `docs/UX-REDESIGN.md` §3.3; an unknown hash opens This Week. The retained DOM ids — `top-picks`, `more-stores`, `big-retailers`, `watchlist`, `price-compare`, `coupons`, `free-food`, `my-list`, plus the functional ids `themeToggle`, `list`, `clear` — each appear exactly once. The legacy store section ids `al-aqsa` and `wfw` are hash routes only, not element ids
3. No external URLs in the page except intentional links (repo/docs links)
4. **Privacy scan (blocking):** search the full publish set for the owner's personal name, home street patterns, and phone-number patterns. A hit stops the push — no exceptions. Only "Stafford, TX 77477" and public store addresses may appear
5. File sizes sane: `index.html` should stay well under 1 MB
6. Service worker cache version bumped if `sw.js` or the shell changed

## Publishing

Publishing is a snapshot push via the GitHub connector (the repo was created by the owner; the connector cannot create repos — its `create_repository` returns 403 for this integration):

1. Confirm the repo's current head matches the last recorded sync entry (the local sync record lives outside this repo, next to the source folder, and lists each confirmed commit SHA with the exact paths submitted)
2. Write a NUL-delimited manifest of the repo-relative paths to publish, stored **outside** the source folder
3. Push with the connector's `push-files` (validated UTF-8 snapshot, single commit, message `HaulBoard: <date or change summary>`)
4. On confirmed success, append the new commit SHA + paths to the sync record (atomic replace). On failure or an uncertain result, do **not** advance the record — reconcile the repo state first; a push that "failed" may have landed
5. Read back the pushed files (`get_file_contents`) and check the commit list
6. Verify the live site at https://ayaan40000.github.io/haulboard/ after the Pages deploy finishes (usually a minute or two) — a successful push is not proof the site updated

GitHub Pages itself is enabled once, by the owner, in repo **Settings → Pages → Deploy from a branch → main / (root)**. There is no connector tool for that toggle.

Note: each connector push may surface an approval card to the owner. If a Friday push sits waiting on approval, the run reports it as not published rather than claiming success.

## Weekly content generation

Friday content is generated by the automated run (see OPERATIONS.md) from that week's captured data and the regenerated category tables — the page is rebuilt, not hand-edited, so structural changes (new views, features) are made here in the source template first and then flow into the weekly rebuilds.

Page structure (app-style since 2026-10-26, spec: `docs/UX-REDESIGN.md`): six views — This Week, Stores (with per-store detail sub-views and the watchlist group), Compare, Coupons, Free Food, My List — one visible at a time via the hash router and tab bar. Weekly data is swapped only between the paired HTML comment markers (`VIEW` / `SECTION` / `STORE` / `DATA`, alone on their own line; full registry in the spec §8.2); the shell inside `SHELL` markers (header, tab bar, core scripts, styles) is frozen for weekly runs. Deal rows carry one priced item each with an Add button (`data-item` = `"<Item> — <Store> — <Price>"`); the My List storage contract (`haulboard-list-v1`) and theme contract (`hb-theme`, `#themeToggle`) must not change, so saved lists and theme choices survive every rebuild. Bump the `sw.js` cache version whenever the shell changes.
